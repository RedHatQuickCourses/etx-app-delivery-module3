Lab 4: Automate the CI Pipeline

In this lab, you’ll configure Tekton Triggers and GitLab webhooks to automatically start the CI pipeline whenever changes are pushed to the application repository.

You’ll create the Tekton Trigger resources, expose an EventListener, configure GitLab to send push events, and verify that commits automatically trigger new PipelineRuns.

By the end of this lab, you will have:

  • Created a TriggerBinding to map GitLab webhook payloads to pipeline parameters

  • Created a TriggerTemplate that generates PipelineRuns

  • Deployed an EventListener to receive GitLab webhook events

  • Exposed the EventListener using an OpenShift Route

  • Configured a GitLab webhook to trigger the pipeline automatically

  • Verified end-to-end CI pipeline automation

Create the Tekton Trigger Resources

Tekton Triggers connect external events, such as GitLab push notifications, to Tekton Pipelines.

In this exercise, you’ll create the TriggerBinding, TriggerTemplate, and EventListener resources required to automatically start a new PipelineRun whenever code is pushed to GitLab.

Create the TriggerBinding

The TriggerBinding extracts values from the GitLab webhook payload and maps them to parameters used by the pipeline.

  1. In the Web Terminal, run:

    oc apply -f - <<'EOF'
apiVersion: triggers.tekton.dev/v1beta1
kind: TriggerBinding
metadata:
  name: gitlab-push-binding
  namespace: etx-app-dev
spec:
  params:
    - name: git-url
      value: $(body.repository.git_http_url)
    - name: git-revision
      value: $(body.checkout_sha)
EOF

The binding maps:

  • The Git repository URL

  • The commit SHA used as the pipeline revision

Create the TriggerTemplate

The TriggerTemplate defines the PipelineRun that Tekton creates when a webhook event is received.

  1. Run the following command:

    oc apply -f - <<'EOF'
apiVersion: triggers.tekton.dev/v1beta1
kind: TriggerTemplate
metadata:
  name: gitlab-push-template
  namespace: etx-app-dev
spec:
  params:
    - name: git-url
    - name: git-revision
  resourcetemplates:
    - apiVersion: tekton.dev/v1
      kind: PipelineRun
      metadata:
        generateName: etx-app-base-app-ci-
      spec:
        pipelineRef:
          name: etx-app-base-app-ci
        params:
          - name: git-url
            value: $(tt.params.git-url)
          - name: git-revision
            value: $(tt.params.git-revision)
          - name: image-name
            value: image-registry.openshift-image-registry.svc:5000/etx-app-dev/etx-app-base-app
        workspaces:
          - name: shared-workspace
            persistentVolumeClaim:
              claimName: pipeline-workspace-pvc
        taskRunTemplate:
          serviceAccountName: pipeline
EOF

The template creates a new PipelineRun using the shared workspace and pipeline ServiceAccount created in the previous labs.

Create the EventListener

The EventListener exposes an HTTP endpoint that receives webhook requests from GitLab.

  1. Run:

    oc apply -f - <<'EOF'
apiVersion: triggers.tekton.dev/v1beta1
kind: EventListener
metadata:
  name: gitlab-listener
  namespace: etx-app-dev
spec:
  serviceAccountName: pipeline
  triggers:
    - name: gitlab-push
      bindings:
        - ref: gitlab-push-binding
      template:
        ref: gitlab-push-template
EOF

The EventListener connects the GitLab webhook to the TriggerBinding and TriggerTemplate.

Expose the EventListener

GitLab must be able to securely reach the EventListener.

  1. Create an HTTPS route:

    oc create route edge el-gitlab-listener \
  --service=el-gitlab-listener \
  --port=http-listener \
  -n etx-app-dev

  2. Retrieve the EventListener URL:

    echo "https://$(oc get route el-gitlab-listener -n etx-app-dev -o jsonpath='{.spec.host}')"

  3. Sample output:

    https://el-gitlab-listener-etx-app-dev.apps.cluster-xxxxx.dynamic.redhatworkshops.io

Copy this URL. You’ll use it when configuring the GitLab webhook.

GitLab requires HTTPS endpoints for webhooks. The OpenShift Route provides TLS termination for the EventListener.

Configure the GitLab Webhook

To allow GitLab to automatically trigger the pipeline, configure a webhook for the application repository.

Creating GitLab webhooks requires Maintainer or Owner access to the project. Administrative configuration also requires the GitLab root account.

Enable Local Network Webhooks

By default, GitLab blocks webhook requests to internal cluster addresses.

  1. Retrieve the GitLab administrator information:

    GITLAB_URL="https://$(oc get route -n gitlab -l app=webservice -o jsonpath='{.items[0].spec.host}')"
GITLAB_ROOT_PASSWORD=$(oc get secret -n gitlab gitlab-gitlab-initial-root-password -o jsonpath='{.data.password}' | base64 -d)

echo "GitLab URL: $GITLAB_URL"
echo "Admin Area: $GITLAB_URL/admin"
echo "Network Settings (Direct): $GITLAB_URL/admin/application_settings/network"
echo ""
echo "Root Username: root"
echo "Root Password: $GITLAB_ROOT_PASSWORD"

  2. Sign in to GitLab using the built-in root administrator account. Click Standard tab (not ETX Lab SSO)

    Figure 1. GitLab Login Page(Click the image to view it in full size in a new browser tab)

    • Username: root

    • Password: Use the password from the command above

  3. Navigate to:

    • Admin Area  Settings  Network

      Figure 2. Admin Area Options(Click the image to view it in full size in a new browser tab)

  4. Expand Outbound requests.

    Figure 3. Outbound Requests(Click the image to view it in full size in a new browser tab)

  5. Enable local network webhooks:

    • Check ☑️ Allow requests to the local network from webhooks and integrations

    • Optionally check ☑️ Allow requests to the local network from system hooks

      Figure 4. Outbound Settings(Click the image to view it in full size in a new browser tab)

  6. Click Save to save the changes.

This setting allows GitLab to communicate with services running inside the OpenShift cluster, including the Tekton EventListener.

Create the Repository Webhook

  1. Navigate back to Admin Area → System hooks

    Figure 5. System hooks menu(Click the image to view it in full size in a new browser tab)

  2. Click Add new webhook.

    Figure 6. Add new hook(Click the image to view it in full size in a new browser tab)

  3. Configure the webhook:

    • URL: Paste the EventListener Route URL by retrieving it from below command.

      echo "https://$(oc get route el-gitlab-listener -n etx-app-dev -o jsonpath='{.spec.host}')"

    • Trigger: Check ☑️ Push events

    • SSL verification: Uncheck for lab environments with self-signed certificates

      Figure 7. Sample Hook Settings(Click the image to view it in full size in a new browser tab)

  4. Click Add webhook

Test the Webhook

Verify that GitLab can communicate with the EventListener.

  1. Select the webhook.

  2. Click Test → Push events.

    Figure 8. Push events(Click the image to view it in full size in a new browser tab)

  3. A successful test returns an HTTP 202 Accepted response.

    Figure 9. Push test results(Click the image to view it in full size in a new browser tab)

Verify Automatic Pipeline Execution

After the webhook is configured successfully, verify that GitLab automatically starts the CI pipeline.

  1. Retrieve the Red Hat Dev Spaces URL by running the following command:

    oc get checluster devspaces -n openshift-devspaces -o jsonpath='{.status.cheURL}{"\n"}'

  2. Open the URL displayed in the output in your web browser and open a terminal inside your workspace.

  3. Push a change to your repository and confirm the pipeline triggers:

    echo "# CI/CD test" >> README.md
git add README.md
git commit -m "Test webhook trigger"
git push origin feature/add-devfile

  4. Monitor PipelineRuns:

    oc get pipelinerun -n etx-app-dev -w

    A new PipelineRun should be created automatically without manual intervention and should Succeeded.

  5. Follow the latest run logs:

    # Get the name of the latest PipelineRun
LATEST_PR=$(oc get pipelinerun -n etx-app-dev --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1].metadata.name}')

echo "Following logs for: $LATEST_PR"

# Follow the logs
oc logs -f $(oc get pods -n etx-app-dev -l tekton.dev/pipelineRun=$LATEST_PR --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1].metadata.name}') -n etx-app-dev

  6. Verify the image was pushed:

    oc get imagestream etx-app-base-app -n etx-app-dev

    You should see the image tagged with the commit SHA.
