= Lab 13: Configure Multi-Cluster Stage Deployment
:navtitle: Lab 13: Stage Deployment
:experimental:

In this lab, you'll prepare the staging environment for multi-cluster deployments by creating stage-specific GitOps manifests and configuring the runtime cluster to securely pull application images from Quay.

By the end of this lab, you will have:

* Created GitOps manifests for the staging environment
* Configured the runtime cluster to authenticate with Quay using an image pull secret
* Updated the staging deployment to use Quay-hosted images
* Committed and pushed the staging manifests to the GitOps repository

== Prepare the Stage Environment

In this exercise, you'll create a staging environment in the GitOps repository based on the existing development manifests.

. Clone the GitOps repository:
+
[source,bash,role=execute]
----
GITLAB_URL="https://$(oc get route \
  -n gitlab \
  -l app=webservice \
  -o jsonpath='{.items[0].spec.host}')"

git clone ${GITLAB_URL}/software-factory/etx-app-gitops.git
cd etx-app-gitops
mkdir -p environments/stage
----

. Copy the development manifests as the starting point for the staging environment.
+
[source,bash,role=execute]
----
cp environments/dev/*.yaml environments/stage/
----

. Retrieve the Quay registry URL that will host promoted application images.
+
[source,bash,role=execute]
----
QUAY_URL=$(oc get route -n quay -l quay-component=quay-app-route -o jsonpath='{.items[0].spec.host}')
echo "Using Quay URL: $QUAY_URL"
----


== Configure Image Pull Access

The runtime cluster must authenticate with Quay before it can pull promoted container images.

. Log in to the https://catalog.demo.redhat.com/catalog/babylon-catalog-prod?item=babylon-catalog-prod/openshift-cnv.app-platform-runtime-cnv.prod&utm_source=webapp&utm_medium=share-link[**Service Enablement: App Platform Runtime**] cluster.
+
[source,bash,role=execute]
----
oc login -u $RUNTIME_USER -p $RUNTIME_PASSWORD $RUNTIME_API --insecure-skip-tls-verify
----
+
NOTE: Make sure you have properly set the `RUNTIME_USER`, `RUNTIME_PASSWORD`, and `RUNTIME_API` values as described in Step 2 of xref:lab-11.adoc#_enroll_the_runtime_cluster[Lab 11: Enroll the Runtime Cluster].
+
. Create a docker-registry secret in `etx-app-staging` on the runtime cluster using the robot account credentials. Replace **$ROBOT_TOKEN** with the etx-app+promoter token:
+
[source,bash,role=execute]
----
oc create secret docker-registry quay-pull-secret \
  -n etx-app-staging \
  --docker-server=$QUAY_URL \
  --docker-username='etx-app+promoter' \
  --docker-password=$ROBOT_TOKEN
----

. Switch back to the factory cluster using the credentials provided by RHDP lab environment page.
+
[source,bash,role=execute]
----
oc login $FACTORY_API -u $FACTORY_USER -p $FACTORY_PASSWORD --insecure-skip-tls-verify
----
+
NOTE: Make sure you have properly set the `FACTORY_USER`, `FACTORY_PASSWORD`, and `FACTORY_API` values as described in Step 2 of xref:lab-11.adoc#_enroll_the_runtime_cluster[Lab 11: Enroll the Runtime Cluster].


== Create the Stage Deployment Manifest

Create a deployment manifest that references the staging namespace and Quay-hosted application image.

. Navigate to the **etx-app-gitops** repository that you cloned previously or freshly clone the **etx-app-gitops** repository locally:
+
[source,bash,role=execute]
----
GITLAB_URL="https://$(oc get route -n gitlab -l app=webservice -o jsonpath='{.items[0].spec.host}')"

git clone ${GITLAB_URL}/software-factory/etx-app-gitops.git
cd etx-app-gitops
----

. Replace the existing deployment manifest with the following configuration.
+
[source,bash,role=execute]
----
cat > environments/stage/deployment.yaml <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: etx-app-base-app
  namespace: etx-app-staging
  labels:
    app: etx-app-base-app
  annotations:
    instrumentation.opentelemetry.io/inject-java: "true"
spec:
  replicas: 2
  selector:
    matchLabels:
      app: etx-app-base-app
  template:
    metadata:
      labels:
        app: etx-app-base-app
      annotations:
        instrumentation.opentelemetry.io/inject-java: "true"
    spec:
      imagePullSecrets:
        - name: quay-pull-secret
      containers:
        - name: etx-app-base-app
          image: ${QUAY_URL}/etx-app/etx-app-base-app:stable
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 500m
              memory: 1Gi
            limits:
              cpu: "2"
              memory: 2Gi
          env:
            - name: POSTGRESQL_HOST
              value: "parasol-db.etx-app-staging.svc.cluster.local"
            - name: POSTGRESQL_DATABASE
              value: "parasol"
            - name: POSTGRESQL_USER
              value: "parasol"
            - name: POSTGRESQL_PASSWORD
              value: "parasol"
            - name: QUARKUS_HIBERNATE_ORM_DATABASE_GENERATION
              value: update
EOF
----

Compared to the development environment, the staging deployment includes several production-oriented changes:

* Deploys to the `etx-app-staging` namespace
* Runs two application replicas for improved availability
* Pulls images from the Quay registry instead of the OpenShift internal registry
* Uses the `quay-pull-secret` to authenticate with Quay

== Update and Commit the Stage Manifests

Update the remaining manifests to reference the staging namespace and commit the changes to the GitOps repository.

. Update the Service and Route manifests.
+
[source,bash,role=execute]
----
sed -i 's/namespace: etx-app-dev/namespace: etx-app-staging/' \
  environments/stage/service.yaml \
  environments/stage/route.yaml
----

. Verify that all manifests reference the staging namespace.
+
[source,bash,role=execute]
----
grep namespace environments/stage/*.yaml
----
+
Sample output:
+
[source,bash]
----
environments/stage/deployment.yaml:  namespace: etx-app-staging
environments/stage/route.yaml:  namespace: etx-app-staging
environments/stage/service.yaml:  namespace: etx-app-staging
----

. Commit and push the staging environment manifests.
+
[source,bash,role=execute]
----
git add -A
git commit -m "feat: add stage environment manifests"
git push origin main
----
+
Once the changes are pushed, the GitOps repository contains separate deployment definitions for both the development and staging environments, enabling Argo CD to manage each environment independently.
